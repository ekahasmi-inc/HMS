Recommended Sprint 1B Structure

Instead of treating all apps equally, split Sprint 1B into smaller milestones.

Sprint 1B
│
├── 1B.1 Identity Foundation
├── 1B.2 Tenant Foundation
├── 1B.3 Subscription & Licensing
├── 1B.4 Configuration Engine
├── 1B.5 Notification Framework
└── 1B.6 Platform Integration

This order reflects the dependency graph.

Sprint 1B.1 — Identity Foundation

Create:

backend/apps/platform/identity/

Purpose:

Everything related to authentication and authorization.

Initial models:

User
Role
Permission
RolePermission
UserRole

Do not add tenant-specific logic yet.

Sprint 1B.2 — Tenant Foundation

Create:

backend/apps/platform/tenants/

Models:

Tenant
TenantDomain
TenantBranding
TenantSettings

Now the SaaS becomes multi-tenant.

Sprint 1B.3 — Subscription & Licensing

Create:

backend/apps/platform/subscriptions/

backend/apps/platform/licensing/

Models:

Plan
Subscription
SubscriptionFeature
License

These determine what a tenant is entitled to use.

Sprint 1B.4 — Configuration Engine

Create:

backend/apps/platform/configuration/

This is one of the most important apps.

It should contain configuration for:

Features

Theme

Menus

Page Layouts

Business Rules

Workflow

Forms

Dashboard

Branding

SEO

Notice that this app should not know anything about bookings or rooms. It only provides the platform's configuration capability.

Sprint 1B.5 — Notification Framework

Create:

backend/apps/platform/notifications/

Models:

NotificationTemplate
NotificationChannel
NotificationLog

Supported channels can later include:

Email
SMS
WhatsApp
Push notifications
In-app notifications

Every future module (booking, CRM, finance, etc.) should use this central notification service.

Sprint 1B.6 — Platform Integration

Only after all previous apps exist should we connect them together.

Why this order?

For example:

Booking needs a tenant before it can create rooms.
Website Builder needs tenant branding and configuration before it can render pages.
CRM needs users, tenants, and subscriptions.
AI depends on data generated by all the earlier modules.

Building in dependency order minimizes refactoring.

Milestone After Sprint 1B

When Sprint 1B is complete, the platform should already support:

Creating a tenant
Assigning a custom domain or subdomain
Creating users and roles
Selecting a subscription plan
Enabling or disabling features
Applying branding and theme
Sending platform notifications

At that point, you have a functioning multi-tenant SaaS platform, even before adding booking, website, or PMS capabilities.

My recommendation before writing any Platform Core code

Before creating the first identity model, let's define the shared relationships that all Platform Core apps will use:

Identity
├── User
├── Role
└── Permission

Tenant
├── Tenant
├── TenantDomain
├── TenantBranding
└── TenantSettings

Subscription
├── Plan
├── Subscription
├── Feature
└── License

Configuration
├── ConfigCategory
├── ConfigKey
├── ConfigValue
└── FeatureFlag

This acts as a mini-ERD for Sprint 1B and ensures the models across these apps fit together cleanly before implementation begins. It will reduce changes later when you start building the Website Platform and Booking Platform.
