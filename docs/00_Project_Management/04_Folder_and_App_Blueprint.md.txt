Sukhavasam SaaS - Folder & Application Blueprint

Version: 1.0

Purpose

This document defines the complete repository layout, Django application structure, package organization, dependency rules, and development conventions.

Once implementation begins, this document becomes the standard for every new app and package.

1. Repository Structure

The repository is organized into logical layers instead of technology layers.

sukhavasam-saas/
│
├── backend/                    # Django backend
├── frontend/                   # Future React / Mobile UI
├── docs/                       # Architecture & documentation
├── deployment/                 # Docker, Nginx, CI/CD
├── scripts/                    # Utility scripts
├── tools/                      # Developer tooling
├── tests/                      # End-to-end tests
├── .github/                    # GitHub Actions
├── .env.example
├── docker-compose.yml
├── Makefile
├── README.md
└── LICENSE

Split models by domain.

Example:

booking/models/
│
├── reservation.py
├── reservation_room.py
├── guest.py
├── room.py
├── room_type.py
├── rate_plan.py
├── inventory.py
├── payment.py
├── invoice.py
└── __init__.py

This keeps each file focused.

6. Shared Package

The shared/ package contains reusable platform utilities.

shared/

├── base/
├── database/
├── events/
├── exceptions/
├── middleware/
├── permissions/
├── storage/
├── utils/
├── validators/

No business logic belongs here.

7. Config Package

Project configuration lives in one place.

config/
│
├── settings/
│   ├── base.py
│   ├── development.py
│   ├── testing.py
│   ├── staging.py
│   └── production.py
│
├── urls.py
├── wsgi.py
├── asgi.py
└── celery.py

Environment-specific settings inherit from base.py.

8. Environment Management

Use environment variables exclusively.

.env

.env.development

.env.testing

.env.staging

.env.production

Never commit secrets.

9. Requirements Management

Split dependencies.

requirements/

base.txt

development.txt

testing.txt

production.txt

This minimizes production dependencies.

10. API Organization

All APIs live under /api/v1/.

booking/api/

views/

serializers/

urls.py

permissions.py

Versioning enables backward compatibility.

11. Service Layer

Every business operation belongs to a service.

Example:

booking/services/

reservation_service.py

pricing_service.py

payment_service.py

checkin_service.py

Views should orchestrate, not implement business rules.

12. Selector Layer

Selectors contain read queries.

booking/selectors/

reservation_selector.py

inventory_selector.py

guest_selector.py

They centralize complex database reads.

13. Repository Layer

Use repositories for complex write logic when needed.

booking/repositories/

reservation_repository.py

invoice_repository.py

Simple ORM operations can stay within services.

templates/

Organize uploaded content by tenant and purpose.

media/
└── tenants/

        ├── branding/
        ├── rooms/
        ├── gallery/
        ├── blogs/
        ├── invoices/

        ├── documents/
        └── users/

This simplifies backup, migration, and deletion.

17. Import Rules

To keep modules loosely coupled:

common may be imported by any app.
shared may be imported by any app.
Domain apps should not directly import each other's models.
Cross-module interaction should happen through services or published interfaces.
Circular imports are not allowed.

Example:

booking
   │
   ├── uses ConfigurationService
   ├── uses PaymentService
   └── does not import finance.models directly

19. Naming Conventions
Apps: booking, crm, website
Modules: reservation_service.py
Models: Reservation
Tables: booking_reservation
Services: ReservationService
Selectors: ReservationSelector
Repositories: ReservationRepository
Exceptions: ReservationException

Consistency is mandatory.

20. Testing Layout

Tests mirror the app structure.

booking/tests/
├── models/
├── services/
├── selectors/
├── api/
├── permissions/
└── integration/

This makes it easy to locate and maintain tests.

21. Documentation Within Apps

Every app should include:

booking/
├── README.md
├── architecture.md
└── api.md

These documents explain the app's purpose, internal design, and public interfaces.

22. Dependency Injection (Future)

Where practical, services should depend on interfaces rather than concrete implementations.

Example:

NotificationService
    ↓
EmailProvider
WhatsAppProvider
SMSProvider

This enables provider replacement without changing business logic.

23. Example Development Workflow

When adding a new module:

Create the app.
Add README and architecture documentation.
Define models.
Create migrations.
Implement selectors.
Implement services.
Add serializers.
Build API/views.
Add tests.
Update roadmap and documentation.

No app is complete until documentation and tests are included.

24. Future Ready

The blueprint is designed to support:

Multi-property hospitality groups
White-label deployments
Mobile apps
Public APIs
Event-driven architecture
Microservice extraction (if ever needed)

without reorganizing the repository.
